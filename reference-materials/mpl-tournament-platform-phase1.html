Statut d’exécution

Une base robuste, mais encore spécialisée

L’application publique a été auditée. Elle présente déjà la majorité des briques sportives nécessaires à un moteur de tournoi premium.

Limite de cette session. Aucun code source n’est présent dans le workspace et aucun Website ID canonique n’est lié. La base Supabase, le dépôt et la production n’ont donc pas été modifiés. Cette approche protège le tournoi CANA de toute migration aveugle ou de la création d’une seconde application.
01 · Current architecture observable

Ce qui existe déjà

L’application est une application Next.js rendue comme un produit de tournoi complet, avec une identité visuelle et éditoriale fortement centrée sur CANA.

Routes publiques observées

Navigation tournoi/, /live, /schedule, /round-robin, /men, /women, /brackets, /ranking-brackets, /teams, /results, /info
Routes de détail/match/[matchId], /teams/[teamId], /posters/[asset]

Administration observée

/admin propose un accès par PIN officiel. La surface actuelle est principalement orientée vers le scoring live.

Capacités réutilisables

  • Match engine, score entry et affichage des scores.
  • Centre live multi-courts, statuts de match et prochain match.
  • Groupes / round robin, tableaux, tableaux de classement et dépendances.
  • Équipes, pages équipes, planning et order of play.
  • Pages de résultats, responsive mobile et bottom navigation.
  • Rafraîchissement automatique des scores et conventions d’URL partageables.
  • Design premium déjà cohérent : navy / near-black, blanc, cyan / bleu et accents gold.

03 · Target architecture

Une application unique, plusieurs compétitions

MPL Platform ├── Public │ ├── /tournaments │ ├── /tournaments/[slug] │ └── /tournaments/[slug]/ │ ├── live │ ├── schedule │ ├── draws │ ├── groups │ ├── teams │ ├── players │ ├── results │ └── info ├── Player ecosystem │ └── /players/[slug] ├── Personal view │ └── /my-tournament └── Admin ├── /admin/tournaments ├── /admin/tournaments/new └── /admin/tournaments/[id]

Le layout MPL reste partagé. Chaque tournoi injecte son identité, sa venue, ses dates, son statut, ses catégories, son branding et ses données sportives. Les moteurs existants restent au centre du produit.

05 · Database migration

Migration CANA sûre et réversible

Pré-requis : ajuster les noms de tables legacy au schéma Supabase réel avant exécution. Le script ci-dessous constitue un socle de migration, pas une autorisation d’exécuter en production sans sauvegarde.

create extension if not exists pgcrypto;

create table if not exists public.venues (
  id uuid primary key default gen_random_uuid(),
  name text not null,
  slug text not null unique,
  address text,
  google_maps_url text,
  logo text,
  contact jsonb not null default '{}'::jsonb,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create table if not exists public.tournaments (
  id uuid primary key default gen_random_uuid(),
  slug text not null unique,
  name text not null,
  short_name text,
  season integer not null,
  level text not null check (level in ('M25','M50','M100','M250','M500','M1000')),
  venue_id uuid references public.venues(id) on delete set null,
  start_date date,
  end_date date,
  registration_open_date date,
  registration_close_date date,
  status text not null default 'DRAFT'
    check (status in (
      'DRAFT','REGISTRATION','DRAW_PENDING','PUBLISHED',
      'LIVE','COMPLETED','ARCHIVED'
    )),
  logo text,
  cover_image text,
  description text,
  organiser text,
  referee text,
  public_url text,
  settings jsonb not null default '{}'::jsonb,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create index if not exists tournaments_status_dates_idx
  on public.tournaments(status, start_date, end_date);

Règles de sécurité

  1. Créer une sauvegarde des tables legacy.
  2. Ajouter tournament_id nullable.
  3. Backfiller toutes les lignes CANA vers m1000-cana-2026.
  4. Comparer les comptes avant / après.
  5. Ne supprimer aucune table ni colonne legacy en Phase 1.
  6. Rendre les contraintes strictes après validation de production.
  7. Afficher un avertissement critique avant toute correction impactant un match terminé.

Tournament Hub

LIVE NOW regroupe les tournois LIVE. UPCOMING regroupe REGISTRATION, DRAW_PENDING et PUBLISHED. RECENT RESULTS affiche les tournois COMPLETED triés par date. ARCHIVE conserve les tournois ARCHIVED.

Homepage tournoi

La page dynamique reprend la qualité visuelle actuelle et remplace le contenu statique par tournament.name, venue.name, les dates persistées, les agrégats filtrés et le statut du tournoi.

Admin tournaments

Créer /admin/tournaments avec filtres Draft / Upcoming / Live / Completed, CTA CREATE TOURNAMENT, action DUPLICATE TOURNAMENT et indicateurs équipes / joueurs / matchs / courts.

Le premier wizard couvre General, Categories, Courts, Branding, Review et Create. Les étapes Points, règles avancées, scheduling et draw sont affichées comme Phase 2.

08 · Non-régression

  • Match engine et score entry.
  • Standings, brackets, classification et dépendances.
  • Realtime Supabase.
  • UI mobile publique.
  • PIN/admin scoring actuel.
  • Teams, groups, matches, schedules et results du CANA.

09 · Prochaine étape

Pré-requis pour l’implémentation réelle

Fournir l’un des éléments suivants :

  1. Le dépôt Git / source checkout de l’application actuelle ;
  2. une archive du code source avec les migrations Supabase ;
  3. le Website ID canonique UUID7.

Le séquencement prévu est alors : website inspect, website status, website source checkout, audit du schéma réel, migration SQL ajustée, routes dynamiques, hub et admin Phase 1, validation locale, puis déploiement.

Décision d’architecture : le tournoi M1000 CANA 2026 devient l’enregistrement permanent m1000-cana-2026. Aucune donnée sportive existante ne doit être supprimée ; elle doit être rattachée à ce contexte tournoi et rester archivée.
